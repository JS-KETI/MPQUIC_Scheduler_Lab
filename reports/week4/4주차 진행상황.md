## 1. 4주차 작업 내용

**스케줄러 이름과 동작 방식**

스케줄러는 데이터를 어느 경로로 보낼지 정하는 방식입니다. RTT(왕복 시간)는 데이터를 보내고 수신 확인이 돌아올 때까지 걸리는 시간입니다.

| 이름 | 이 실험 코드에서의 동작 방식 |
|---|---|
| RR | 전송할 때마다 활성 경로를 차례로 하나씩 선택 |
| MinRTT | 두 경로 중 왕복 시간이 짧은 경로를 우선 사용하고, 보낼 여유가 없으면 다른 경로 선택 |
| BLEST | 왕복 시간이 짧은 경로가 막히면, 지연이 큰 경로로 보낼지 기다릴지 판단 |
| ECF | 남은 데이터량·전송 여유·왕복 시간으로 완료 시간을 추정해, 기다릴지 다른 경로로 보낼지 판단 |
| Peekaboo | 왕복 시간이 짧은 경로를 우선 사용하고, 막히면 경로 상태와 이전 전송 결과에 따른 점수로 선택 |
| MinRTT-multi | 한 번의 선택에서 지금 데이터를 보낼 여유가 있는 모든 경로를 함께 사용 |
| EAT | 예상 도착 시각이 빠른 경로를 우선 사용하고, 전송 완료에 도움이 되는 다른 경로도 함께 사용 |
| ID 7 기본 모드 | 새 알고리즘을 넣기 위한 확장 번호. 이번 4경로 테스트의 기본 모드는 MinRTT-multi와 동일하게 동작 |

- **그림의 시간·횟수 읽는 법**
  - 평균 전송 완료 시간
    - 완료 처리된 실행에서, 전송 시작부터 코드의 완료 기준에 도달할 때까지 걸린 시간의 평균
  - 완료 처리와 전체 수신
    - `완료`: 목표량보다 3,000B 적게 받아도 충족하는 코드 기준. `전체 수신`: 목표 바이트를 모두 받은 실행
    - `5/5`는 전체 5회 중 5회. `완료 없음`은 평균을 계산할 완료 실행이 없다는 뜻
  - 조건·시나리오
    - `열화 후 경로 1 속도 3Mbps`: 전송 중 경로 1의 속도를 3Mbps로 변경한 실험
    - `dominating`: 한 경로가 속도·지연 모두 유리. `competing`: 빠른 경로의 지연이 더 큼. `degrade`: 전송 중 경로 1 성능 저하

1-1~1-4는 통합 수정 전 측정 결과이며, 특이사항·원인별 수정은 2절, 같은 조건 전체의 통합 수정 후 결과는 3절에 정리했습니다.

    - 기존 완료 실행의 미완료 전환 7회가 남아 통합 수정의 회귀 검증 전체 통과는 보류. 후보 브랜치와 측정 결과 보존
    - 공식 기준선 교체·브랜치 병합·5주차 알고리즘 구현은 진행하지 않음
  - 기준 대조
    - 기존 공통 코드 버전의 공식 2주차 기준값·4주차 최초 동결 결과는 보존
    - 기존 조건의 완료·전체 수신은 105/105회 유지. 공식 2주차 기준값과 RESULT 9항목이 모두 같은 실행은 0/105회이며, 전송 시간·경로별 바이트 등 변경된 코드 버전의 측정값은 별도 보존
