## 1. 4주차 미완료 원인 분석

- **분석 범위 (미완료 277회 전체 재현·원인별 분류)**
  - 대상
    - 본 측정 1,163회 중 미완료 277회. 손실률 0.1% 7회, 손실률 1% 74회, 100패킷 큐 87회, 1MiB 버퍼 105회, 50MiB 장시간 전송 4회
    - 강건성 테스트는 3개 시나리오·7개 스케줄러·seed 1~5, 장시간 테스트는 seed 1~10
  - 검증 방법
    - 종료 상태·송신 대기량·수신 순서 대기량·재전송 묶음 크기를 기록한 뒤, 원인별 수정 후보를 별도 실행
    - 완료 처리는 목표량보다 3,000B 적게 수신한 시점. 전체 수신은 목표 바이트와 실제 수신량이 정확히 같은지 확인
    - 전송은 시뮬레이션 시각 1초에 시작. 완료 시간(FCT)은 시작 이후 경과 시간이며, 제한 시각 60·180·300·600초는 시뮬레이션의 절대 시각
  - **결과**
    - **277회 모두 원래 21개 측정 항목과 일치. 관찰 코드를 추가해도 최초 미완료 결과 유지**
    - **원인 관찰·후보 수정·시간 연장을 합해 추가 954회 실행. 기존 동결 결과와 공식 2주차 기준값 보존**
    - **확장 조건에는 사전 제공 기준값 없음. 기존 조건 105회의 공식 기준값 일치와 별도로 분석**

## 2. 원인별 검증 결과와 개선 방법

### 2-1. 보낼 데이터가 남았는데 연결 종료 (78회)

- **종료 조건 확인 (전송 중 목록과 전송 대기 목록을 구분)**
  - 최초 문제 상황
    - 손실 조건에서 ACK(수신 확인)를 처리한 뒤 연결이 닫히고 수신량 증가 중단
  - 원인
    - `QuicSocketBase::OnReceivedAckFrame`에서 전송 중 목록만 비었는지 확인하고 `Close()` 호출
    - 종료 후 최종 관찰 시점에도 소켓에 아직 보내지 않은 프레임 157,465~5,246,877B가 남아 있음
  - 수정 후보
    - 전송 중 목록이 비었고 소켓의 전송 대기량도 0일 때만 종료하도록 조건 추가
  - **결과**
    - **원래 제한 시각 60초에서 59/78회 완료·전체 수신**
    - **나머지 19회는 같은 수정에 제한 시각 300초를 적용했을 때 19/19회 완료·전체 수신**
  - 개선 시 확인할 사항
    - 소켓뿐 아니라 스트림의 남은 데이터까지 확인하는 종료 조건 필요
    - 300초 결과는 원래 60초 실험과 분리. 같은 제한 시각의 성능 개선으로 합산하지 않음

### 2-2. 스트림에 남은 데이터를 다시 넘기지 못함 (68회)

- **송신 재개 경로 확인 (소켓에 공간이 생긴 뒤 스트림 잔량 전달)**
  - 최초 문제 상황
    - 1MiB 버퍼에서 앱은 목표 5,242,880B를 스트림에 넘겼지만, 스트림에 947,560~1,048,300B가 남은 상태로 정체
  - 원인
    - 소켓 공간 부족으로 스트림에 남겨 둔 데이터를 ACK 수신 후 다시 넘기는 경로가 없음
    - 앱은 스트림이 데이터를 받았다는 반환값으로 전송을 마치므로, 이후 새 앱 전송으로 재개되지 않음
  - 수정 후보
    - ACK 수신 후 소켓에 여유가 생기면 스트림 잔량 전달 재개
    - 2-1의 소켓 잔량 확인 조건 함께 적용. 버퍼 4종은 모두 1MiB 유지
  - **결과**
    - **이 그룹 65/68회 완료·전체 수신. 나머지 3회는 수신 버퍼 부족으로 연결 중단**
    - **1MiB 전체 105회에서는 69/105회 완료·전체 수신. 남은 36회 모두 수신 버퍼 부족 기록 확인**
  - 개선 시 확인할 사항
    - 전송할 공간이 생기는 시점에 스트림 잔량을 재개하고, 앱 종료와 실제 송신 완료를 구분

### 2-3. 수신 순서를 맞추는 버퍼 부족 (37회)

- **작은 수신 버퍼 확인 (먼저 올 데이터를 기다리는 동안 저장 공간 소진)**
  - 최초 문제 상황
    - 앞부분이 비어 있는 상태에서 뒤쪽 데이터가 쌓여, 수신 측이 연결을 중단
  - 원인
    - `QuicStreamBase`가 순서가 뒤바뀐 데이터를 보관하다 1MiB 수신 버퍼 한계에 도달
    - 37/37회에 `Aborting connection due to full RX buffer` 기록. 최초 중단 시뮬레이션 시각 2.580605~2.987968초
  - 수정 후보
    - 수신 스트림 버퍼만 1MiB → 8MiB 변경. 나머지 송수신 버퍼 3종은 1MiB 유지
  - **결과**
    - **버퍼 부족에 의한 연결 중단은 37/37회에서 사라짐. 다른 송신·종료 문제로 전체 수신은 0/37회**
    - **스트림 잔량 전달·소켓 종료 조건까지 함께 바꾼 105회 실험은 98/105회 완료·전체 수신**
    - **남은 7회는 스트림에서 목표 끝까지 수신했지만 앱에 전달된 바이트가 부족**
  - 남은 원인 추정
    - 순서가 맞춰지며 한꺼번에 전달되는 데이터가 1MiB 소켓 수신 버퍼에서 거절될 가능성. 코드 경로는 확인했으나 거절 바이트를 직접 기록한 검증은 미수행
  - 개선 시 확인할 사항
    - 버퍼를 키우는 설정 완화와, 작은 버퍼에서도 수신 가능량을 제한하고 데이터를 안전하게 나누어 앱에 전달하는 구현 개선을 구분

### 2-4. 재전송 데이터 묶음·분할 처리 (87회)

- **재전송 크기와 프레임 경계 확인 (100패킷 큐에서 손실 후 재전송)**
  - 최초 문제 상황
    - 87회 모두 UDP/IP가 담을 수 있는 크기를 넘는 67,548~397,211B의 QUIC 프레임 묶음을 송신 시도
    - 앞부분 미수신으로 뒤쪽 데이터만 쌓이거나 이후 수신이 중단
  - 원인
    - `DoRetransmit`이 여러 손실 패킷의 데이터를 합한 크기를 한 번의 송신 요청으로 전달
    - 크기 제한만 적용한 run-15에서 추가로 확인한 분할 한계: 재전송 항목에는 여러 STREAM 프레임(스트림 번호·위치·데이터를 담는 단위)이 들어갈 수 있으나, 기존 분할 처리는 한 프레임을 전제로 함
  - 수정 후보
    - 재전송 항목을 STREAM 프레임별로 다시 나눈 뒤, 각 송신량을 MSS(한 번에 보내는 기본 데이터 크기) 수준으로 제한
    - 큐 100패킷·버퍼 40,000,000B·제한 시각 60초 유지
  - **결과**
    - **프레임별 분리와 크기 제한을 함께 적용하면 87/87회 완료·전체 수신. 완료 시간 3.2735~10.6182초**
    - **크기 제한만 적용한 앞선 시도는 0/87회 전체 수신. 실패 기록도 보존**
  - 개선 시 확인할 사항
    - 일반 코드에 적용하려면 제어 프레임·빈 종료 프레임·헤더 해석 실패·추가 헤더의 바이트 계산을 보완하고 회귀 검증 필요
    - 거대 묶음의 수신 부재는 확인했으나, 각 패킷이 큐·IPv4 분할 중 어느 단계에서 소실됐는지까지 모두 확정하지 않음

### 2-5. 제한 시각까지 전송 중인 실행 (7회)

- **시간 연장 검증 (코드 수정 없이 60초 → 300초·180초 → 600초)**
  - 최초 문제 상황
    - 원래 종료 직전에도 앱 수신량이 증가. 프로세스 오류나 수동 중단 없이 설정한 시뮬레이션 시각에 종료
  - 접근 방법
    - 기존 코드·스케줄러·전송량을 유지하고 제한 시각만 연장
  - **결과**
    - **손실률 1%·degrade의 RR seed 3·5, EAT seed 3은 3/3회 전체 수신. 완료 시간 60.6172~66.7356초**
    - **50MiB·competing의 BLEST seed 4·7, ECF seed 8은 3/3회 전체 수신. 완료 시간 183.0382~231.6114초**
    - **50MiB·competing·BLEST seed 10은 계속 미완료. 연장 중 소켓 잔량을 남기고 연결 종료하는 별도 문제 확인**
  - 후속 후보 확인
    - 장시간 BLEST seed 10에 종료 조건 후보와 600초를 함께 적용해도 52,378,670/52,428,800B 수신으로 미완료
    - 수신 측 연결 종료·유휴 타이머의 영향은 추가 확인 대상
