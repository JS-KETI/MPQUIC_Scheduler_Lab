# 미완료 원인 분석 교차 검토

- **조사 범위:** seed 1~30의 미완료 62개 스케줄러–시나리오–seed 조합 전체. 기존 완료 처리 568개 실행의 수신량·완료 시간 변화도 전체 재검증에서 대조.
- **제공 기준 대조:** seed 1~10의 미완료 19개는 제공 기준과 동일. seed 11~30의 미완료 43개는 제공 기준 없음·추가 측정 결과.
- **검토 방법:** 최초 분석 가설의 반례 확인 → 원본 로그 재대조 → 원인별 단독 수정 결과 대조. 같은 링크 속도·지연·목표량·혼잡 제어·seed·완료 기준 유지.

## 2. 후보 B — 이미 전달한 스트림 데이터가 다시 들어오면 앱 전달 바이트가 부족해지는 문제

- **최초 문제 상황:** 끝부분 수신량 부족 54개는 모두 이미 전달한 offset(스트림 내 바이트 위치)보다 작은 프레임이 다시 수신됨. 심한 수신 정체 8개에서는 이 현상이 관찰되지 않음.
- **문제 원인 추정:** 처음에는 마지막 데이터 재전송 누락·조기 연결 종료를 우선 검토. 그러나 일부 실행에서 스트림 기대 offset은 목표 끝까지 전진했는데 앱 수신량만 부족해 이 가설만으로 설명되지 않음.
- **문제 원인 검증:** `GetDeliverable()`은 현재 기대 offset 이후의 연속 데이터 길이를 계산하지만 `Extract()`는 버퍼 맨 앞의 오래된 데이터를 먼저 검사. 앞선 중복 프레임이 더 크면 추출 결과가 없는데 스트림 기대 offset은 계산한 길이만큼 증가하는 경로 확인.
  - 대표: competing·MinRTT-multi·seed 2의 기대 offset은 5,242,860B까지 전진. 앱 수신량은 5,237,104B, 오래된 프레임은 2개 수신.
  - 회귀 사례: 0~199B 전달 → 0~99B 중복 수신 → 250~299B 대기 → 200~249B 수신. 앱에 준비된 데이터는 중복 제외 정확히 300B여야 함.
- **조치:** 완전히 이미 전달한 범위는 제외. 일부만 겹치는 프레임은 아직 전달하지 않은 부분만 처리. 버퍼를 꺼낸 뒤 실제 추출한 payload 크기만큼 기대 offset 증가.
- **조치 후 검증 결과:** 후보 B만 적용한 원래 미완료 62개 중 54개 완료 처리·전체 수신. 심한 수신 정체 8개는 미완료 유지 → 서로 다른 원인으로 분리.

## 3. 후보 C — 누락 프레임이 남아도 마지막 ACK 번호가 데이터 송신 목록에 없어 손실로 판단하지 못하는 문제

- **최초 문제 상황:** 심한 수신 정체 8개는 최초 누락 offset 이후 수 MB가 순서 대기 버퍼에 쌓임. 해당 offset을 포함한 프레임은 원본에서 송신됐지만 수신 기록 없음.
- **문제 원인 검증:** `OnAckUpdate()`의 손실 판정은 ACK가 보고한 마지막 패킷이 데이터 송신 목록에 있을 때만 시작. ACK 전용·probe(전송 상태를 확인하는 시험 패킷) 번호는 그 목록에 없을 수 있어, 더 오래된 미확인 데이터의 재전송 판단이 누락됨.
  - 회귀 사례: 데이터 packet 10 미수신 → ACK가 packet 20과 9 이하 수신을 보고 → packet 20은 데이터 목록에 없음. 기존 번호 차이 기준 3을 넘는 packet 10만 손실로 판단해야 함.
- **조치:** 마지막 ACK 번호보다 오래된 미확인 데이터에 기존 패킷 번호 차이 기준 3을 직접 적용. 스케줄러·혼잡 제어·제한 시간·링크 조건·전송량·완료 기준 유지.
- **조치 후 검증 결과:** 후보 C만 적용한 8개 모두 완료 처리·5,242,880B 전체 수신. 동일 누락 범위의 재전송과 실제 수신은 7개에서 직접 확인. 나머지 1개는 앞선 전송 시각이 바뀌며 해당 범위를 첫 송신으로 수신한 경우.

## 4. 확정 범위와 남은 한계

- **확정:** 이번 seed 1~30의 미완료 62개는 원인별 단독 수정 B 54개·C 8개로 완료 처리와 전체 수신 복구 확인. 스케줄러 성능 평균에서 빠졌던 실행을 실제 수신 데이터 처리·손실 감지 수정으로 복구.
- **전체 검증 결과:** 수정 조합을 적용한 630개 전체에서 기존 완료 568개의 완료 처리는 유지. 정확 수신 신규 미달 4개·일부 전송 시간 증가를 확인했으며 아래 6절에 별도 기록. 단독 수정 실험만으로 부작용이 없다고 판단하지 않고 전체 대조 결과를 함께 보존.
- **최초 패킷 폐기 지점 확인:** 원본 심한 정체 8개 모두 기본 FqCoDel 큐의 지연 목표 초과 폐기에서 최초 누락 프레임의 QUIC 패킷 번호 직접 확인. 첫 IP 조각이 폐기되어 IPv4 재조립이 실패한 증거는 아래 7절 참조.
- **후보 A:** 소켓 수신 추출의 erase 후 iterator 참조·크기 계산 결함은 별도 범위. 이번 62개의 해결 건수에 포함하지 않음.
- **대기 버퍼 내부의 부분 겹침:** 후보 B는 이미 앱에 전달한 범위만 제거. 아직 대기 중인 프레임끼리 다른 offset으로 겹치는 일반 경계 사례는 별도 범위이며 이번 62개 원인으로 확인하지 않음. 모든 형태의 스트림 겹침을 해결한 것으로 확대하지 않음.
- **시간 기반 손실 판정:** 기본 실험에서 비활성. 수정의 검증 범위는 패킷 번호 차이 기반 판정이며, 다른 손실 옵션·다른 패치 구성은 검증하지 않음.
- **채택하지 않은 가설:** 여러 STREAM 프레임을 합친 재전송 패킷의 재분할 오류는 코드상 우려가 있으나, 이번 62개의 원인이라는 직접 증거 없음.
- **완료 판정 보존:** 이번 조사에서는 목표량에서 3,000B 적게 받아도 완료 처리하고 10ms 뒤 종료하는 기존 기준을 변경하지 않음. 완료 처리와 정확한 전체 수신 수치는 계속 분리.
- **주차 진행 범위:** 미완료 원인 분석 승인과 게이트 2의 신뢰구간 적용 대상 확인은 별도. 이번 결과만으로 3주차 진입을 승인한 것으로 처리하지 않음.

### 6-1. 기존 완료 568개 seed의 전송 완료 시간 변화

- **계산:** 원본·수정이 모두 완료 처리한 같은 seed끼리 FCT(코드 완료 기준까지의 경과 시간)를 비교. 평균 차이 = 수정 − 원본, 양수는 수정에서 더 오래 걸림. 두 값 모두 기록된 0.0001초 단위로 계산.
- **95% 신뢰구간:** 같은 seed 시간 차이 평균의 추정 구간. t 분포 기반 양측 구간이며 상한 − 하한이 폭.
- **Wilcoxon:** 시간 차이의 절대값 순위로 양측 유의확률 계산. 차이 0인 seed 제외, 같은 차이는 평균 순위, 순위 부호의 모든 조합을 정확 분포로 계산. 0 차이가 많아 정규 근사의 유효 표본 수가 작아지는 문제를 피함. `critical-review-paired-times.csv`에 기록.
- **568개 시간 변화:** 빨라짐 135개, 동일 266개, 느려짐 167개. 같은 조건에서 전송 시간까지 모두 개선됐다는 근거는 없음.

## 7. 최초 데이터 폐기 지점 — 기본 FqCoDel 큐와 IP 조각 재조립 (8개 직접 매핑)

- **원본 대조:** 추가 관찰 실험 `12-original-qdisc-observe`의 8개 결과값은 기존 원본 관찰 실험과 9개 지표 모두 동일.
- **최초 폐기:** FqCoDel(큐 대기 지연을 줄이려고 패킷을 폐기하는 기본 큐 관리 기능)이 `Target exceeded drop`으로 첫 IPv4 조각을 폐기. 큐 길이 overflow로 단정하지 않음.
- **하위 계층 결과:** 첫 조각 offset 0B는 수신 노드 5에 도달하지 않음. 나머지 조각만 도착한 뒤 재조립 제한 시간이 지나 `DROP_FRAGMENT_TIMEOUT`(코드 6)으로 폐기.
- **미복구 원인:** QUIC 손실 감지에서 마지막 ACK 패킷이 데이터 송신 목록에 없는 경우 누락 데이터가 손실 판정에서 빠져 재전송되지 않음. 패킷 폐기 발생과 복구 누락을 별도 원인 단계로 구분.
- **손실률 0의 의미:** `LossRate=0`은 실험의 확률적 수신 오류 모델을 끈 설정. 기본 큐의 지연 목표 초과 폐기까지 비활성화한 설정은 아님.

## 8. 최종 코드 검토 — 중복 payload와 함께 처음 도착한 FIN 보존

- **발견한 회귀 가능성:** 초기 수정 B는 이미 전달한 payload 전체를 중복으로 판단하면 FIN(해당 스트림의 마지막 바이트를 알리는 종료 표식)을 처리하기 전에 반환. 같은 데이터를 다시 보내면서 처음 FIN을 붙인 프레임의 종료 상태가 반영되지 않는 경로 확인.
- **조치:** 주 에이전트가 원본 FIN 검사와 수신 상태 갱신을 먼저 수행하도록 변경. FIN 없는 완전 중복은 제외하고, FIN 있는 완전 중복은 payload를 0B로 줄인 뒤 원래 범위 끝의 offset을 유지해 기존 종료 처리로 진행.
- **독립 회귀 테스트:** 0~199B 전달 → 동일 범위 200B에 첫 FIN을 붙여 수신. 수신 상태 `DATA_READ`, 애플리케이션 대기량 200B, 실제 바이트 순서 0~199B를 각각 확인. 중복 payload는 새 애플리케이션 데이터로 추가되지 않아야 함.
- **FIN 수정 전후 대조:** `regression-latest-before-fin.json`에서 초기 A+B+C 수정은 첫 FIN의 `DATA_READ` 상태 검사 1개 실패. FIN 보존 수정 후 `regression-latest-final.json`에서 종료 상태·대기량 200B·실제 바이트 순서 3개 모두 통과. 바이트 중복 제거와 종료 표식 처리를 독립 확인.
- **전체 재검증 완료:** FIN 보존 수정 후 코드·바이너리·라이브러리 해시를 기록한 `14-fin-preservation-full-630/`에서 같은 630개 조합 재실행. 완료 처리 630/630·정확 전체 수신 621/630, 중복·누락·실행 오류 0개. 독립 대조에서 `08-combined-full-630`과 630개의 9개 측정 항목 차이 0개. 이번 FIN 보완 후에도 위 6절의 수신량·시간 변화 집계 유지.
- **packet 내부 부분 읽기 검증:** 13B·7B·31B를 넣고 5B → 17B → 나머지 순서로 읽어 packet 내부의 두 분할 경계를 확인. 반환량 5B·17B·29B, 대기량 46B·29B·0B, 이어 붙인 51B의 실제 순서를 확인하는 7개 검사 모두 통과.
- **최종 회귀 결과:** 같은 최종 테스트 소스의 원본 스택은 소켓 14개·스트림 5개·손실 3개 검사 실패. 최종 수정 스택은 세 실행 모두 실패 0개. 초기 FIN 누락은 수정 전 A+B+C 스택에서 별도 1개 실패로 재현했고 최종 수정에서 통과. 실패 실행·최종 실행의 명령과 소스 해시를 각각 보존.
- **독립 보고서 대조:** 원인 B 54개·C 8개, 제공 seed 1~10의 19개·추가 seed 11~30의 43개, 원래 미완료 62개 전체 수신 회복, 신규 정확 수신 미달 4개·기존 미달 5개, 공통 완료 568개 시간 변화 135개·266개·167개가 분석 CSV와 일치. 21개 조합 집계를 다시 계산했으며 동결 파일 27개 해시도 직접 계산해 보존 확인.
- **검토 범위:** 생산 코드의 FIN 처리 순서와 테스트 실제 payload 순서까지 대조. 대기 중 서로 다른 프레임끼리의 부분 겹침·선택형 시간 기반 손실 감지·시간 증가 원인은 기존 추가 조사 대상으로 유지.
